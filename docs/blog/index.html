Proving Python correct by Verifying Correctness

A deterministic transpiler, the seven design decisions behind it, and why the translation step is the one place a language model must not be.

By Anirudh Gupta17 October 2026~25 min read

A test tells you your code works on the inputs you thought of. A proof tells you it works on every input there is. This is the new notion of correctness that the world is adopting. Formal verification is a field of computer science which helps you in showing correctness of software by mathematically proving it(notion of correctness depends on whatever you want) and computer scientists have been developing this field ever since theory of computer science came about.

However, most people never try proving correctness and go for testing, because the languages where you can write proofs — Lean 4, Rocq, Dafny, F\* — are not the ones anyone writes programs in. The code that needs checking is in, say Rust or Python, a language every developer these days use and quite popular for AI development. Since correctness of your program is very important for you, your company, research lab, etc., great deal of time and effort goes in finding the right and "exhaustive" set of tests to see if things work. Yet this does not rule out possibility of corner cases and such bugs are quite hard to find. Now, as you just read in previous line what formal verification can do for you, is rule out possibility of any such bugs if you prove your code is correct, want to see if it works. But you have a problem, that would have to convert logic/algorithm you write in the Python, in some other language like Lean4 for formal verification.

Good news is that Agents in 2026 are super smart that they can do the conversion for you, but do you trust their implementation of your code? Do you trust the notion of correctness they used in proving your theorem? Let me fill in the mind gap for you.

From the picture above, all you need is a verified and trustable tool to convert your code(Python, Rust, etc.) in Lean4 and write the correctness theorem you described. Now you can employ an agent to fill the proof which Lean4 can check. Thus you have successfully removed the "non-determinism" in your pipeline and you can rest assure that the AI didn't do anything wrong, it just can't.

PastaLean(comes from Py+AST+Lean) is the tool you would want to use to fill in that gap. You write ordinary Python. A fixed, deterministic translator turns it into Lean 4. Lean then checks it — and if you have said what the code is supposed to do, Lean proves it.

A Hoare triple, read as a sentence: assuming P holds, running prog leaves Q true. P comes from Requires in the Python, Q from Ensures.

Why this matters more than it did two years ago

An enormous share of the Python running in the world right now was drafted by a language model. Agentic systems lean on it even harder: they write a script, run it, read the number, and build the next step on that number. If the script is subtly wrong, the conclusion is wrong, and nothing in the pipeline notices. And as you would know, model's can convince you that a wrong answer is in fact correct!

As discussed before, testing is the usual answer and a weak one here, because the tests are written by the same process that wrote the bug(the agent). If you employ a model for this task again, you trod the way of non-determinism and blind shooting the correctness aim, only hoping the gun is good enough.

Proving things instead sounds unaffordable. It is not, for a reason specific to how agents work. An agent generates a lot of exploratory code and only a small slice of it feeds the final answer, the main logic. That slice is the only part worth proving, and proving it blocks nothing, because verification runs in parallel with the exploration that follows. You are not paying to verify everything — only the handful of functions whose output someone will act on. This is a design choice that I emphasize on since proving stub code like writing to files, loading datasets, making network connections, etc. doesn't give you as much value since they are mostly IO work. However, any logic that goes into the algorithm of how data is processed, is very important and correctness is invaluable.

Lean 4 suits this because it is two things at once: a proof assistant with a friendly, super-smart people behind it, a mathematics library called Mathlib and Computer Science library called CSLib, and a real compiled language that goes through C to native code. So the translated program can actually run, at competitive speed, and be reasoned about — and the reasoning reuses Mathlib instead of a verification stack built for this one purpose.

Why not just ask a model to write the Lean from Python?

This is the obvious shortcut, and rejecting it is the most important decision in the project. Three reasons, in increasing order of force.

It is not reproducible. Run a model twice and you get two translations. There is no line in any table you can point at and say this is why append became pyAppend. Auditing a non-deterministic translator audits one sample of it.

It defeats the purpose. A model translating Python to Lean might quietly fix the bug: clean up an off-by-one, pick the sensible branch, write the code you obviously meant. Desirable in an assistant, fatal in a verifier — a model can translate incorrect Python into correct Lean. The proof closes, you ship, and the bug is still sitting in the Python that actually runs. The method does not get weaker. You may counter that models are smart these days to not pull it off. You wanna bet with your software?

And it measures poorly comparatively. We tested on Claude Opus 4.8 with a benchmark of Python source, the same test harness PastaLean is scored with, the signature pinned in the prompt so the output is callable, five independent samples per problem at temperature 1.0.

The number to look at is the distance between pass@5 and pass⁵. On LiveCodeBench the model finds a working translation within five tries three-quarters of the time, and produces five that all work less than a third of the time. That spread is the unreliability. A deterministic transpiler has pass⁵ equal to pass@1 by construction, because there is only ever one output. (When the model failed it was usually by calling a Mathlib lemma that does not exist under that name, or writing a recursive def Lean cannot show terminates.)

Two neighbouring questions. Why not write in a verification language like Dafny from the start? Because the risk just moves to the specification: if the spec is mistranslated from what you meant, your code is provably correct about the wrong thing and nothing flags it. Why write the specifications in Python rather than Lean, then? You can actually, and I would recommend it too. A lot of specifications might not be writable in Python due to less mathematical notation availability meanwhile Lean provides an aresenal of all Mathematics to back you up and support you. You can write it in Python or Lean and PastaLean will pick it up for you.

Now that we know PastaLean is the right tool for you, let's dive into how it works.

How PastaLean cooks

PastaLean converts Python to its Abstract Syntax Tree(AST) from where it is transpiled into Lean. The process of converting a language into another is called transpilation. There are net Four stages in this conversion.

Parse. Python's own ast module does it, so there is no second grammar to keep in sync with CPython. The tree becomes JSON, one object per node, tagged with its node_type.

Annotate. Lean needs a type for every binder; Python supplies almost none. A type inference engine TypeInfer (more below) walks the IR and writes a _ty field onto every binder whose type it can work out — and changes nothing else. No expression is rewritten, no node removed. That restraint is the point: the generator reads an inferred type in exactly the place it reads a hand-written annotation, so there is no second code path, and a fully annotated program produces identical Lean whether the engine ran or not.

Generate. Each IR node type has a Lean function registered against it by an attribute — @[pygen "FunctionDef"], @[pygen "BinOp"] — and a dispatcher looks the function up by node_type and calls it, recursing into children. Supporting new Python syntax means writing one tagged function; nothing else in the pipeline changes.

One quiet detail is load-bearing. These generators do not return strings. They return Lean's own typed syntax objects, so Lean's compiler type-checks the generator itself: a generator cannot emit something that is not well-formed Lean. The output then goes through Lean's elaborator, which decides whether it type-checks against the runtime.

This is another design paradigm while working with Lean: the Lean elaborator is the oracle. We are not comparing output against a golden file written by hand. We are asking a compiler whether the translation makes sense(type checking), and it answers for every program, including the ones nobody thought to test.

PastaLean conversion is very fast, and it can convert your most files within a second on a warm backend. One practical note: the expensive part is loading Mathlib, four to five seconds. So the generator runs as one persistent backend that statements are streamed into, paying that cost once for a whole dataset rather than once per file.

Understanding an Example

This is HumanEval problem 85 — add the even elements at odd indices. First the Python, with its specification written in it. Note that the Final Condition is chosen to be a simple one in this example however you can write it to be as complex as your needs support.

Python
from contracts import *

def add(lst):
    Requires(len(lst) > 0)
    # THE POINT: only even elements are ever added, so the answer is even.
    Ensures(Result() % 2 == 0)

    s = 0
    for i in range(1, len(lst), 2):
        Invariant(s % 2 == 0)          # the running sum stays even
        Invariant(1 <= i)              # index bounds, so lst[i] is defined
        Invariant(i < len(lst))
        Invariant(i % 2 == 1)          # range(1, _, 2) yields only odd indices
        if lst[i] % 2 == 0:
            s += lst[i]
    return s

Requires, Ensures and Invariant are imported from a small module and are thin wrappers around assert, so this file still runs under CPython exactly as before — the contract behaves like an ordinary assertion while your test suite exercises it. The translator, though, does not evaluate them. It lifts them out of the syntax tree and turns them into the statement of a theorem.

Design choices

Lean is statically typed functional programming language, meanwhile Python is a dynamically typed Object Oriented language. Python and Lean disagree about almost everything that matters: mutation, types, objects, effects, numbers. Every one of those disagreements had to be settled in a particular direction, and the direction was almost always chosen to protect provability. Let's understand some of them in order to strengthen the concepts around this tool.

What we support

The sections below are the choices that shaped everything else, but it helps to see the surface they cover first. PastaLean targets the part of Python that logic is actually written in:

  • Values and operators — int, float, bool, str, tuples, list, dict, set, slicing, f-strings, chained comparisons, and Python's own //, % and **.
  • Control flow — if/elif/else, for, while, break/continue, match, list/dict/set comprehensions and generator expressions.
  • Functions — default arguments, several returns of different types, nested functions, closures, currying, decorators, lambda, yield, @cache.
  • Objects — classes with __init__, methods, @staticmethod/@classmethod/@property, dunder operators, single and multiple inheritance.
  • Effects — try/except/finally, raise, print, input.
  • Libraries — math, typing, heapq, numpy, pandas, scipy, and anything else somebody writes a mapping for.
  • Contracts — Requires, Ensures, Invariant, Decreases, Assert, all written in Python.

Every item on that list is a Python feature that Lean does not have in the same shape, so every one of them is a decision. Here are the seven that the rest follow from.

1. Every function is translated twice

One Python function becomes two Lean definitions: foo, the provable twin, and foo'rn, the runnable one — same IR, same generators, differing in only a few places.

Hover or click any name below for its real type, docstring or proof state — this is the Lean compiler's own data.

Why not just pick one? Because the two jobs want opposite things.

For proving, a Python float becomes an exact rational, ℚ. Lean has a Float, but it is IEEE floating point: 0.1 + 0.2 is not 0.3, and you cannot build a proof on arithmetic that is approximately true. And a Python list becomes Lean's List, because List is what Mathlib's thousands of lemmas are stated about.

For running, both choices are bad. List is a linked list, so appending is O(n) and indexing position i costs O(i), where Python's list is a dynamic array and both are constant time. A loop that is linear in Python becomes quadratic in Lean. Apart from this, since proving does not require IO side effects, Exceptional handling(apart from passing down information), we have special duals for both provable and runnable twin. The provable twin is primarily a noop, but a runnable twin behaves like how Python would behave, printing statements, throwing exception errors, etc.

2. Pure vs Monadic Functions

Lean distinguishes pure functions from ones that have side-effects, which become monadic. PastaLean tries to lower each function to the least powerful shape that can express it:

  1. a plain term, for a function that just computes;
  2. Id.run do, for local mutation and loops — imperative to read, still pure, because Id is the identity monad;
  3. an exception monad, for raise / try / except;
  4. real IO, only when the program talks to the outside world.

The reason to stay low is simple: it is easier to prove pure functions than monadic A plain term can be proved about directly. An Id.run do block needs Hoare triples to specify the postconditions to prove, depends on precondition and loop invariants given by you. IO action is opaque and its result depends on the world making it significantly harder to prove. This motivates behind the design choice of keeping the logic(to be proved) separate from IO based operations.

The runnable twin uses IO and ExceptT, while the provable twin uses a pure exception layer, so divide is a no-op for external effects. Even print follows this pattern: it is a no-op in the provable twin, while the runnable twin performs the real output. Nothing is discarded, no effect escapes, and what a program prints becomes a value a theorem can talk about.

3. Operators are typeclasses whose result type is computed

Python's + is not one operation. It adds numbers, concatenates strings and lists, treats booleans as integers so that True + True is 2, and mixes numeric types freely. Lean's + does none of this.

So each Python operator gets its own class — PyHAdd, PyHSub and so on, written +ₚ and -ₚ — with the result type as an outParam, computed from the operands rather than supplied by the caller. The conversions do not depend on which operator you are using, so they are declared once in a single class recording how any two numeric types meet, and one generic instance per operator reads them off. Generated code therefore never states a result type: int + float lands on a rational by itself. The examples below pin their operands only because a bare literal in isolation has no type.

Two things come free with the class, and they are the reason it is a class and not a function. The first is every other Python name whose meaning depends on what you hand it: len is one class with one instance per container, so len([1,2,3]), len("Hello") and len({"k": "v"}) are a single name with three implementations, and a proof about lists never has to step around the string case. The second is the last line of the snippet. Where Python's operator agrees with Lean's, the instance delegates straight to Lean's, which is why Mathlib's existing theorems about + apply to +ₚ unchanged.

Agreement is the exception, though, and the disagreements are the dangerous part. Mathlib already defines addition on lists, and it defines it pointwise. If Lean reaches that instance first, [1,2] + [3,4] quietly elaborates to [4,6] instead of [1,2,3,4] — a wrong answer that no type error will ever catch, in a program that compiles cleanly. Our instance is declared at a higher priority so Python's reading wins. Instance priority is not a tuning knob here; it is the semantics.

The same care applies to numbers. Python's tower is bool < int < float, and a value widens only at the operator that mixes it with a wider one — driven by the operands, never by the surrounding context, so a -> float annotation does not make an integer variable a float. Python's / is always float division, so 7 / 2 is a rational in the provable twin and a Float in the runnable one even though both operands are integers. And // rounds toward negative infinity while % takes the sign of the divisor, where Lean's Int division truncates: 7 // -2 is -4 in Python and -3 in Lean, 7 % -2 is -1 against 1. Both conventions are defensible and neither raises an error, which is precisely what makes the disagreement dangerous.

We have made Lean definitions which implement Python's builtins — len, sorted, abs, divmod, zip, sum, min, max, chr, ord, the int, str, float, list, set and dict constructors — plus other string, list, dict and set methods. Two lookup tables connect the languages: one is a match on names, so len(xs) becomes pyLen xs, and one does the same for methods, so s.split(",") becomes pyStringSplit s ",".

4. Python mutates objects; Lean rebuilds values

Python containers are mutable objects. Lean values are not. So every in-place mutation becomes a rebuild-and-rebind:

Python
xs.append(3)      #  ->  xs := pyAppend xs 3
d[k] = v          #  ->  d  := pySetItem d k v

The runtime helper returns a new container and codegen stores it back into the same let mut name. That reads as though it copies the whole list on every append, and it does not. Because the name is rebound, nothing else holds the old value, and Lean's reference counting mutates the buffer in place when a value has exactly one owner. The runnable twin gets Python's constant-time append out of a translation that is purely functional on paper — which is the only reason the array backing from choice 1 is fast and sound.

The same mismatch shows up with names instead of values. Python is function-scoped: a variable first assigned inside an if, a for or a try is still visible after that block ends. Lean is block-scoped, so that binding would die with the block. Codegen therefore hoists it — one let mut y : T := default before the outermost block that needs it, with every assignment inside becoming a reassignment of that single variable.

Python
for i in range(n):
    for j in range(n):
        y = i * j      # first bound in the inner loop
return y               # still visible here, so `y` is declared before the outer loop

The type T comes from the inference engine. Only def, lambda and comprehensions get a scope of their own, which is exactly Python 3's rule.

5. Nested functions are lifted, generators are computed up front

Lean has no nested def, and no mutable enclosing scope for a closure to point back at. So a nested function becomes a sibling private partial def whose captured names are extra parameters, filled in at every call site; what gets lifted is precisely the names the inner function reads that the outer one binds, so globals and builtins stay out. When the closure escapes as a value — returned from its parent, or a decorator's wrapper — we emit a genuine Lean closure that partially applies the sibling with the captures baked in. Returned closures, currying and decorators all work, and the sibling keeps its simp tag, so they stay provable.

Why a sibling rather than Lean's own where? Because a where clause inherits partial from the definition it sits inside, so the enclosing function would become partial, lose its unfolding and stop being provable — the helper's convenience would cost the proof you wanted. Lifting confines partial to the helper. The rule for which names get lifted is subtle enough that its scope-preservation argument is itself machine-checked in Lean.

yield is handled in the same spirit: a generator's body is rewritten to build a list and return it, so every consumer — for x in g(), list(g()), sum(g()), a comprehension — sees an ordinary list and no separate machinery for lazy streams exists at all. The rewrite runs before type inference, which is what gives the accumulator a real element type and makes recursive generators and generator pipelines work. The price is honest and listed later: computing the sequence up front means an infinite generator consumed lazily never finishes.

@cache is the one place the twins differ in algorithm rather than representation. The provable twin stays the plain recursion, because that is the shape induction reasons about. The runnable twin threads one hash map through the recursion, so an exponential cached dynamic program runs in polynomial time. Memoization returns the same answers either way, so the twins still agree on what is computed — only on how long it takes.

6. Classes are values, and the heap is opt-in

A Python class becomes a Lean structure paired with a namespace of functions. Attributes are fields, __init__ becomes C.new, a method takes self as an ordinary first argument, and a method that mutates self returns an updated object which the call site rebinds — value semantics, exactly as in choice 5. Dunders map onto the typeclasses carrying the same notation, so __add__ keeps working as +ₚ instead of turning into a named call, and __str__ makes print(obj) print. Inheritance is structure Derived extends Base, which embeds the parent's fields.

This is faithful whenever an object has a single handle, which covers most of the code we target, and it keeps the program in the pure fragment where Lean's equational reasoning works directly. It is wrong the moment a program aliases. In Python b = a makes two names for one object, and incrementing through b is visible through a; under value semantics the two names hold two values, and the program quietly computes a different answer.

The fix is deliberately not a change to the default. Reference semantics is a second, opt-in tier (--heap), so a program pays for a heap only when it needs one. There, a heap is a map from addresses to values, the translated program runs in a monad carrying that heap alongside Python's exceptions, every value Python passes by reference is allocated in it and represented by a typed reference Ref α, and attribute reads and writes go through that reference. Aliasing then works with nothing special done for it, because b = a copies an address.

Two things stop the tier from being a tax on the whole program. An analysis across function calls decides which functions actually need the heap monad, so pure helpers keep their pure translation. And specifications are separation-logic Hoare triples: the precondition names only the cells the function touches, and Lean's vcgen carries everything else across the call automatically. So a heap appears only where the program has one, and a proof mentions only the object it is about.

And when a line has no translation at all. Real Python is full of statements that carry no logic — logging, a progress print, a metrics call — and a translator that stopped at the first logging.getLogger would be useless on exactly the code we want to verify. Such a line becomes a placeholder holding its own source text: the binding still elaborates, the variable stays declared, a linter warns you, and the loop doing the real work is translated and verified as normal, while --strict turns the placeholder into a hard error for anyone who would rather not have one. The cost is measured, not asserted — 5 of 2,589 LeetCode problems are skipped for importing something outside the supported set, and HumanEval translates with zero placeholders.

Does it work? The Layer of Trust

After understanding briefly about the internal working of PastaLean, a question may arise is,

How do you know PastaLean is correct?

Proving correctness of a transpiler cannot be proved formally without writing a Python interpreter which is a very hard task. We do not claim either that PastaLean is 100% bug free either, since we donot model all of Python and capturing semantics of a dynamically typed object oriented Programming language into Lean comes with great deal of design decisions to make it correct.

Hence, in such places, we must go with emperical evidence for how good PastaLean is.

We evaluate on three benchmarks with two questions each: does the generated Lean compile, and does it compute what Python computes. A program counts as elaborated when its Lean type-checks. A solution counts as passed only when the runnable twin returns CPython's answer on every one of the dataset's own test cases — not most of them.

The most useful result is the failure analysis. The 13 HumanEval programs that do not elaborate are mostly not generator bugs. They are genuine type ambiguities:

Python
def split_words(txt):
    # words on whitespace, else on commas, else a letter count
    if any(c in txt for c in ' \n\r\t'): return txt.split()
    if ',' in txt: return txt.split(',')
    return sum(1 for c in txt if c.islower() and (ord(c) - ord('a')) % 2 == 1)

For most inputs this returns a list of strings. For an input with no spaces and no commas it returns an integer. Both are correct Python. Nothing in the code or the signature says which one this function "is" — it depends on the input, at run time. Python is fine with that. Lean is not, because a function has one return type.

Add a single type hint at the ambiguous spot and all 13 compile: 164 of 164. That is the honest shape of the limitation. It is not "the tool is 92% good". It is "92% of these need nothing from you, and the rest need one word."

Two proofs, start to finish

Everything above is one piece of the pipeline at a time. Here are two whole ones, taken from the five problems the paper works end to end, and these are the two hardest of the five. Pick one and read it in two steps: the Python with its contract attached, then the Lean that came out of it with the proof that closes it. Nothing is abridged — the proof is the file exactly as it is committed, and it is interactive because it compiles.

Nested loops. Six invariants on the outer loop and two on the inner, and from them three postconditions: the answer is no longer than n, and every entry lies in the window 2 … n-1.

1 · The Python, carrying its contract

Python
from typing import *
from contracts import *

def count_up_to(n: int):
    """Implement a function that takes an non-negative integer and returns an array of the first n
    integers that are prime numbers and less than n.
    """
    Requires(n >= 0)
    # THE POINT: the answer is drawn from the window {2, ..., n-1} — the sieve only ever appends
    # its own loop counter, which runs over exactly that range — and since at most one number is
    # appended per counter value, the list can never be longer than n.
    Ensures(len(Result()) <= n)
    Ensures(all(2 <= p for p in Result()))
    Ensures(all(p < n for p in Result()))
    ans = []
    isprime = [True] * (n + 1)
    for i in range(2, n):
        Invariant(2 <= i)
        Invariant(i <= n)
        Invariant(len(isprime) == n + 1)
        # At most one append per counter value.
        Invariant(len(ans) <= i)
        # Everything appended so far was a counter value already passed.
        Invariant(all(2 <= p for p in ans))
        Invariant(all(p < i for p in ans))
        if isprime[i]:
            ans.append(i)
            for j in range(i + i, n, i):
                # Index bound for `isprime[j]`.
                Invariant(2 <= j)
                Invariant(j < n)
                isprime[j] = False
    return ans

2 · The Lean it becomes, and the proof that closes it

The postcondition restates the entire function as a summation, so proving it means proving the loop computes that sum and nothing else. The heaviest of the paper's five.

1 · The Python, carrying its contract

Python
from contracts import *

def double_the_difference(lst):
    '''
    Given a list of numbers, return the sum of squares of the numbers
    in the list that are odd. Ignore numbers that are negative or not integers.
    
    double_the_difference([1, 3, 2, 0]) == 1 + 9 + 0 + 0 = 10
    double_the_difference([-1, -2, 0]) == 0
    double_the_difference([9, -2]) == 81
    double_the_difference([0]) == 0  
   
    If the input list is empty, return 0.
    '''
    # No precondition: the recorded inputs deliberately mix ints, floats and negatives, so any
    # `Requires` restricting the element type would be false.
    #
    # The point: the result is the sum of squares over exactly the positive odd integers of `lst`
    # (floats and non-positives contribute nothing), hence it is a sum of odd squares.
    Ensures(Result() == sum([v * v for v in lst if v % 2 == 1 and v > 0 and "." not in str(v)]))
    # An odd square is odd, so the parity of the answer is the parity of the number of contributors.
    Ensures(Result() % 2 == len([v for v in lst if v % 2 == 1 and v > 0 and "." not in str(v)]) % 2)
    Ensures(Result() >= 0)

    ans = 0
    for num in lst:
        Invariant(ans >= 0)
        if num % 2 == 1 and num > 0 and "." not in str(num):
            ans += num ** 2

    Assert(ans >= 0)
    return ans

2 · The Lean it becomes, and the proof that closes it

What to watch for is where the human work actually goes. The theorem statement is not written by hand: it is generated from the Requires and Ensures lines sitting in the Python. The loop invariants are not either — each Invariant(...) becomes one bullet of the mvcgen call. What is left for a person, or for a model with a person checking it, is the tactic script underneath: the argument for why those invariants survive a round of the loop and together give the postcondition. That is the one step nobody has automated, and these two show how much of the rest is already machinery.

TypeInfer: The type inference engine

One structural problem remains. Lean fixes a definition's parameter types before it looks at the body, so every binder needs a type up front. Python supplies almost none — and the hints it does supply are not enforced:

Python
def add(a: int, b: int) -> int:
    return a + b

add("Hi", "!")      # this works fine. Python does not check the hints.

So a hint is evidence, not truth, and most code carries none. PastaLean ships its own engine, TypeInfer, to recover the rest: it gives every IR node a type from a small lattice, joins in whatever each statement implies, and repeats until nothing changes. Because the engine is itself written in Lean, the laws it rests on are machine-checked — the join really is the least upper bound, and widening a type never excludes a value the program can produce.

One detail shows it is inferring rather than guessing. Python promotes silently, so True + 1 is 2 and a list holding both 5 and float('inf') is a list of floats. The join therefore widens along Python's own tower, bool < int < float. A flat design would send join(int, float) to the top of the lattice and box an entirely ordinary list, losing provability for no reason.

When the join genuinely does reach the top — a parameter used at incompatible types by different callers, a function returning a string on one path and an integer on another — the value is boxed as PyAny, a tagged union. That keeps the translator total: the program compiles and runs instead of being rejected. The cost is provability, since a boxed value is not a commutative ring and the algebra tactics stall on it. But not all of it:

Hover or click any name below for its real type, docstring or proof state — this is the Lean compiler's own data.

pyany_cases splits the goal into one case per runtime type the value could hold, closes every mismatched combination automatically, and leaves real goals stated in Int, String and so on. And here is the part I like: commutativity of this boxed + is not provable, which is the correct answer — on strings and lists it concatenates, so a ++ b = b ++ a is false. The split establishes a property exactly where it holds and nowhere else.

The first is per file. On TypeEvalPy every ground-truth annotation is one fact keyed by its source location, and a tool is scored by how many facts it recovers by exact match. On the large autogen set — 5,453 snippets, 77,268 facts — it is the best static tool on the leaderboard:

The two tables answer two different questions. The per-file numbers say the lattice and the fixpoint are right. The repository numbers say the pass that flows types across imports is right — and that is the one a transpiler actually depends on, since a function you call is usually defined in another file.

The speed comes from what it does not do. Inference is a pure JSON-to-JSON computation that never touches a Lean environment, so it ships as a binary that never loads Mathlib and starts in 30 milliseconds; and because what a snippet infers depends only on that snippet, thousands of them run as independent tasks in one process sharing one read-only copy of the code, where the checkers it is compared against load a full checking state per worker. The known gap, plainly: no union types yet, so int joined with str is boxed rather than typed int | str.

Discussion: Eating PastaLean everyday, Making your code Healthier and Fit

Let's discuss about impacts of PastaLean in verifying correctness of your software and how it changes the way you ship your production code. As mentined before, the division of labour falls out of the design almost mechanically. The model writes the Python, you propose the correctness specification. A fixed translator does the translation. Agent proves it and Lean checks correctness. Each party does the thing it is actually reliable at, and the model is never in the trusted path for meaning.

The contract is the real interface here, and its being Python is underrated. It is the one artifact a human has to read and agree with, and the review question is small and concrete: does this sentence say what I wanted? In case you employ it for writing the specification, it is ultimately your job to make sure that the contracts of correctness cannot be wrong. A human must sit in the loop to make sure the right thing is being proved. Your job of writing code, proving it correct and shiping it is now just boiled down to Is this correctness notion for your code Correct? And don't worry, in case the code or the specification is wrong, Lean will never prove it correct, so rest assured that you are in good hands.

PastaLean ships an MCP server, so a model can drive it directly: annotate, translate, read back the open obligations, attempt them, call the verifier. A Lean certificate means, The checker's verdict is the only Trustworthy verdict. and backing your software with such a certificate is the upcoming future.
